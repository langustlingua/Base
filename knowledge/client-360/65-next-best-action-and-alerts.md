# 65. Next best action, рекомендации и alerts

## Цель

Next best action (NBA) — не автоматическая команда «написать клиенту». Это объяснимая рекомендация: какое действие сейчас принесёт пользу семье и бизнесу с наименьшим риском.

Действием может быть:

- ничего не делать;
- исправить данные;
- ответить человеку;
- помочь со входом;
- открыть задачу поддержки;
- дать релевантный учебный шаг;
- проверить платёж;
- поставить контакт на паузу;
- запросить ручное решение;
- отправить разрешённое сообщение.

## 1. Модель кандидата

| Поле | Назначение |
|---|---|
| `action_candidate_id` | UUID |
| `family_id` | семья |
| `action_type` | справочник действия |
| `reason_code` | почему возникло |
| `source_event_ids` | доказательства |
| `benefit_score` | ожидаемая польза 0–100 |
| `urgency_score` | срочность 0–100 |
| `risk_score` | риск 0–100 |
| `confidence` | exploratory / directional / strong |
| `earliest_at`, `due_at` | окно |
| `blocking_conditions` | что запрещает выполнение |
| `success_event` | результат |
| `expires_at` | когда устаревает |
| `owner_type` | system / operator / support / owner |

Пример ранжирования:

`priority = 0.4*urgency + 0.4*benefit + 0.2*confidence - 0.6*risk`

Формула стартовая и должна калиброваться. P0 privacy/security и просроченные обещания ранжируются правилами, а не формулой.

## 2. Блокирующие условия

NBA не исполняется, если:

- нет нужного согласия;
- contact disputed/invalid;
- открыта privacy/security проблема;
- есть complaint;
- клиент ответил и ждёт человека;
- событие уже устарело;
- результат уже достигнут;
- достигнут frequency cap;
- предложение/цена истекли;
- данные противоречат друг другу;
- действие затрагивает ребёнка без подходящего взрослого;
- система не уверена в связи личности.

## 3. Правила по этапам

### Новый лид

| Условие | Рекомендация | Владелец | Стоп |
|---|---|---|---|
| заявка валидна, доступ не создан | создать доступ/проверить интеграцию | operator/system | trial created |
| контакт не подтверждён | попросить безопасное подтверждение | system | verified/explicit no |
| дубль вероятен | ручная проверка | operator | merge/split decision |
| вопрос в комментарии | ответить до автоматического прогрева | operator | answer sent |

### Пробник

| Условие | Рекомендация |
|---|---|
| письмо доставлено, входа нет | проверить барьер входа |
| письмо bounced | выбрать разрешённый резервный канал/ручная задача |
| вход есть, урок не начат | указать один конкретный стартовый шаг |
| активность начата, нет завершения | предложить помощь по упражнению |
| first value есть | показать результат взрослому |
| повторный сеанс есть, checkout нет | объяснить продолжение и тариф |
| есть вопрос | conversation lock, ответ человека |

### Покупатель

| Условие | Рекомендация |
|---|---|
| payment success, нет entitlement | P1 финансово-техническая задача |
| доступ есть, нет первой сессии | onboarding help |
| активность стабильна | не мешать; отчёт по выбранной частоте |
| 7/14 дней без активности | диагностика причины, затем мягкий возврат |
| milestone | признать прогресс |
| повторные ошибки | учебная помощь, не продажа |
| nearing end | понятные варианты продления |

### Деньги

| Условие | Рекомендация |
|---|---|
| pending слишком долго | сверка с провайдером |
| failure технический | дать безопасный повтор |
| repeated failure | ручная помощь |
| refund requested | остановить маркетинг и сообщать статус |
| refund completed | сверить доступ/чек/комиссию |
| chargeback | finance + owner review |

### Отношения

| Условие | Рекомендация |
|---|---|
| обещание скоро истекает | напомнить сотруднику, не клиенту |
| обещание просрочено | эскалация |
| день рождения + opt-in | поздравление без продажи |
| хороший доказанный результат | позже попросить честный отзыв |
| open case | не просить отзыв/реферал |

## 4. Выбор «не писать»

`no_contact` — полноценный NBA, когда:

- семья активно учится и не просила напоминаний;
- недавно был человеческий контакт;
- нет новой пользы;
- все данные основаны на слабом сигнале;
- нет согласия;
- сейчас идёт решение проблемы;
- сообщение повторит уже известное;
- ожидается подтверждение внешней системы.

Система должна уметь объяснить паузу так же хорошо, как отправку.

## 5. Alerts

Alert — исключение, требующее внимания. NBA — рекомендация. Не каждое NBA становится alert.

### P0

- возможная утечка/неправомерный доступ;
- контакт после opt-out;
- детские данные показаны не той роли;
- конфликт личности при платеже/возврате;
- массовая ошибочная отправка.

### P1

- payment success без доступа;
- refund SLA breached;
- критический support case без ответа;
- просроченное обещание клиенту;
- hard bounce у единственного канала для активного сервиса;
- массовый сбой webhook.

### P2

- лид без обработки в SLA;
- пробник не доставлен;
- repeated login failure;
- расхождение сверки;
- рост отписок/жалоб;
- необычный рост пропусков.

### P3

- неполные данные;
- occasion скоро;
- experiment reached sample threshold;
- template review due.

## 6. Anti-noise

- объединять одинаковые alerts в incident;
- cooldown на повтор;
- alert только при изменении состояния;
- показывать количество затронутых объектов;
- автоматически закрывать при подтверждённом recovery;
- иметь владельца и SLA;
- еженедельно удалять бесполезные правила;
- измерять false-positive и ignored rate.

## 7. Объяснимость

Карточка рекомендации:

> Рекомендуется помочь со входом до 18:00. Причины: доступ создан 3 часа назад; письмо доставлено; входа нет; открытых обращений и запретов нет. Уверенность: directional. Стоп: первый вход, ответ клиента, открытие поддержки.

Запрещено показывать «ИИ решил» без факторов, правил и альтернатив.

## 8. Рекомендации на основе вопросов

Частые вопросы не означают автоматически, что клиент или креатор «плохо понял». Проверять сочетания:

| Сигнал | Возможный вывод | Действие |
|---|---|---|
| много вопросов + высокая конверсия | вовлечение/интерес | сделать FAQ, не обвинять источник |
| много вопросов + низкая конверсия | неясность обещания | улучшить объяснение и тестировать |
| мало входов после заявки | операционная доставка | чинить доступ, не контент |
| first value есть, checkout низкий | оффер/цена/условия | проверить продуктовый барьер |
| продажи есть, возвраты высокие | mismatch ожиданий | остановить масштабирование |
| вопросы после оплаты | onboarding/support gap | исправить продукт и инструкции |

Показывать sample size и альтернативные объяснения.

## 9. Feedback loop

После действия сохранять:

- выполнено/отклонено/просрочено;
- кто решил;
- причина override;
- фактический outcome;
- время до результата;
- негативные последствия;
- стоит ли изменить правило.

Нельзя обучать модель на простом факте «оператор нажал выполнить»: важен outcome.

## 10. Критерии приёмки

- одновременно показывается одна главная и до трёх вторичных рекомендаций;
- P0/P1 не скрываются marketing задачами;
- NBA отменяется при stop event;
- слабый сигнал помечен низкой уверенностью;
- есть вариант `no_contact`;
- оператор видит факторы и может отклонить с причиной;
- override записан;
- правила для ребёнка требуют подходящего взрослого;
- false-positive и ignored alerts измеряются;
- система не делает психологических, медицинских или финансовых выводов о семье.
