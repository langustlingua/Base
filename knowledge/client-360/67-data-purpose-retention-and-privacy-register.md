# 67. Реестр целей, сроков хранения и privacy-by-design

## Статус документа

Это технический и операционный реестр, а не юридическое заключение. Конкретные основания, тексты согласий, уведомления, локализация и сроки обязательного хранения должны быть подтверждены юристом для фактической модели бизнеса и используемых сервисов.

## 1. Главное правило

Для каждого поля и события заранее известны:

- цель;
- субъект;
- источник;
- обязательность;
- правовое/договорное основание;
- получатели и роли;
- место хранения;
- срок;
- правило удаления/анонимизации;
- можно ли использовать для маркетинга, аналитики и ИИ;
- передаётся ли внешнему обработчику.

Если цель отсутствует, данные не собираются.

## 2. Классы данных

| Класс | Примеры | Базовый доступ |
|---|---|---|
| public configuration | схемы, справочники, шаблоны | публичный GitHub допустим |
| operational | статус задачи, обезличенный reason code | staff by role |
| personal | имя, email, телефон | authorised operations |
| child personal | имя ребёнка, класс, прогресс | ограниченные роли |
| financial | оплаты, возвраты, чеки | finance/owner/necessary support |
| communications | переписка, вопросы, заметки | support/operations |
| authentication | sessions, verification, external IDs | technical/limited |
| sensitive/restricted | спор личности, privacy case, специальные потребности | named roles only |
| secrets | API keys, bot tokens, passwords | secret manager only |

Секреты никогда не являются частью Client 360 или GitHub.

| Purpose | Необходимые данные | Не использовать для |

| `billing` | плательщик, order/payment | поведенческий таргетинг |
| `support` | контакт, case, необходимые логи | скрытый маркетинг |
| `learning_progress` | student, activity aggregates | публичное сравнение детей |
| `parent_reporting` | прогресс, предпочтение | реклама третьих лиц |

## 4. Field-purpose record

Для каждого поля:

| Поле | Значение |
|---|---|
| `entity_name`, `field_name` | техническая ссылка |
| `data_class` | класс |
| `subject_type` | guardian/student/family/creator |
| `purpose_keys` | список целей |
| `required` | must/should/optional |
| `collection_source` | форма/API/оператор/derived |
| `source_of_truth` | система |
| `legal_basis_status` | proposed/reviewed/approved |
| `retention_class` | код срока |
| `access_roles` | роли |
| `exportable` | да/нет/с ограничением |
| `deletion_action` | delete/anonymize/retain_restricted |
| `processor_list` | внешние сервисы |

| `review_due_at` | дата проверки |

Канонический машинный реестр — [data-purpose-register.json](data-purpose-register.json).

## 5. Retention classes

Точные сроки утверждаются отдельно. Архитектура поддерживает:

| Класс | Логика |
|---|---|
| `R0_EPHEMERAL` | часы/дни: коды, временные payloads, raw debug |
| `R1_SHORT` | краткий операционный срок: raw web events, failed attempts |
| `R2_ACTIVE_RELATIONSHIP` | пока активна заявка/обучение/поддержка |
| `R3_CONTRACT_TERM` | период услуги + утверждённый срок претензий |
| `R4_LEGAL_ACCOUNTING` | обязательный срок по применимым требованиям |
| `R5_CONSENT_PROOF` | доказательство и история отзыва по policy |
| `R6_AGGREGATE` | обезличенный агрегат без возможности обратной идентификации |
| `R7_UNTIL_WITHDRAWAL_OR_EXPIRY` | UGC/relationship permission |

В коде хранить `retention_class`, а фактическое количество дней — в версионируемой policy, чтобы срок можно было изменить контролируемо.

## 6. Стартовая матрица минимизации

| Данные | Минимум | Усиленный вариант только при цели |
|---|---|---|
| взрослый | имя для обращения + контакт | полное ФИО для договора/чека |
| ребёнок | имя/псевдоним, класс, курс | полная дата рождения только при доказанной цели |
| день рождения | MM-DD | полный год/дата при отдельной необходимости |
| сайт | session, page, event, engaged time | Webvisor/recording после отдельной оценки |
| обучение | агрегат активности и milestone | сырые ответы/голос при учебной необходимости |
| контакт | summary + source reference | полная копия переписки при необходимости |
| платёж | сумма, статус, provider reference | банковские реквизиты не хранить |
| UGC | разрешённый asset и scope | лицо/голос/имя только по отдельным permissions |

## 7. Дети

- взрослый представитель связывается с ребёнком явно;
- доступ к детским данным ограничен;
- точные даты, школа, адрес, расписание и геолокация не собираются без строгой цели;
- маркетинговые выводы по ребёнку запрещены;
- публичная карточка UGC использует псевдоним/аватар по умолчанию;
- прекращение участия в UGC не лишает доступа к обучению;
- публикационные права отделены от сервисной обработки;
- любой takedown имеет SLA и audit.

## 8. Согласия

Согласие должно быть разделено по purpose и каналу. Минимум:

- обработка заявки/услуги;
- email marketing;
- messenger marketing;
- необязательная аналитика;
- birthday;
- testimonial;
- photo/video/voice publication;
- platform list;
- paid advertising;
- editing/derivatives;
- duration.

История append-only. Отзыв не стирает доказательство прежнего статуса, но прекращает будущую обработку по цели и запускает removal workflow.

## 9. Preference center

Пользователь может:

- видеть активные email/телефоны и маскированные каналы;
- управлять темами и частотой;
- отключить маркетинг по каналу;
- отключить поздравления;
- выбрать отчёты;
- исправить дату;
- запросить доступ/исправление/удаление;
- отозвать UGC permission;
- увидеть дату последнего изменения.

Критические сервисные сообщения объясняются отдельно и не смешиваются с маркетинговыми настройками.

## 10. Внешние обработчики

Для каждого сервиса вести:

- назначение;
- категории данных;
- субъектов;
- географию обработки/хранения;
- договор/условия;
- sub-processors;
- security controls;
- deletion procedure;
- export/portability;
- инцидентный контакт;
- дата review;
- владелец подключения;
- способ отзыва ключей.

Новый сервис нельзя подключать «через OAuth на всякий случай»: нужны минимальные scopes и запись в реестре.

## 11. Удаление и анонимизация

Workflow:

1. проверить личность заявителя;
2. определить scope;
3. поставить маркетинговую паузу;
4. найти данные во всех системах и backups по реестру;
5. отделить то, что должно ограниченно сохраняться;
6. удалить/анонимизировать;
7. передать deletion request обработчикам;
8. пересчитать aggregates, если возможна re-identification;
9. сохранить минимальный audit факта выполнения;
10. сообщить результат.

Delete не означает просто `archived=true`.

## 12. Public GitHub boundary

Разрешено:

- SQL DDL без данных;
- JSON Schema;
- синтетические UUID и примеры;
- справочники;
- business rules;
- тексты-шаблоны без получателей;
- тестовые fixtures с явно вымышленными значениями.

Запрещено:

- реальные ФИО, email, телефоны;
- имена и даты детей;
- выгрузки CRM/Метрики/ProgressMe;
- письма и чаты;
- платежи/чеки;
- ClientID/UserID;
- токены/пароли/ключи;
- ссылки на закрытые файлы;
- raw payloads и backups.

## 13. Privacy review перед релизом

- цель документирована;
- собран минимум;
- согласие/основание проверено;
- ребёнок учтён;
- роли и маскирование настроены;
- processor зарегистрирован;
- retention/delete реализованы;
- export/DSR поддерживаются;
- logs не содержат PII/secrets;
- аналитика не передаёт PII;
- тестовые данные синтетические;
- есть stop/rollback;
- владелец и review date назначены.

## 14. Критерии приёмки

- ни одно production-поле не существует без purpose owner;
- точная дата рождения не обязательна для пробника;
- consent по email не открывает Telegram/MAX;
- удаление purpose выключает связанные автоматизации;
- retention job создаёт отчёт и audit;
- processor deletion отслеживается;
- restricted поля маскируются;
- public repository проходит secret/PII scan;
- данные ребёнка не видны внешнему креатору;
- любой сотрудник может объяснить, зачем хранится поле и когда оно удалится.

## 15. Официальные ориентиры для юридической проверки

- Роскомнадзор: согласие должно быть конкретным, информированным и сознательным.
- Для обработки данных ребёнка в случаях, когда требуется письменное согласие, используется согласие законного представителя.
- Реклама по сетям электросвязи требует доказуемого предварительного согласия адресата; burden of proof лежит на распространителе.
- Документация Яндекс Метрики отдельно описывает ClientID/UserID, собираемые данные и ограничения на передачу данных.

Перед запуском проверить актуальные редакции требований и фактическую конфигурацию всех форм, доменов и обработчиков.
