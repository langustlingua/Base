# 61. Дневники, журналы и память о клиенте

## Назначение

Система должна помнить факты и договорённости так, чтобы семье не приходилось каждый раз рассказывать всё заново. При этом CRM не должна превращаться в неструктурированное досье.

Главное правило: факт, событие, сообщение, вывод, задача и заметка — разные сущности.

## 1. Что чем является

| Тип | Пример | Где хранить |
|---|---|---|
| факт | оплачено 3 900 ₽ | payment/ledger |
| событие | первый вход 21 сентября | events |
| сообщение | письмо доставлено | message delivery |
| входящий вопрос | «как выбрать тему?» | interaction + question |
| договорённость | «ответим завтра до 14:00» | promise |
| действие | позвонить 22 сентября | task |
| вывод | риск ухода высокий | derived signal + reason |
| решение | дать паузу до 1 октября | decision log |
| заметка | краткий контекст разговора | journal entry |

Нельзя хранить оплату только в заметке, а обещание — только внутри переписки.

## 2. Типы журналов

### Журнал контактов

Фиксирует входящие и исходящие контакты по email, Telegram, MAX, WhatsApp, телефону, сайту, форме, кабинету и лично.

Минимум:

- канал и направление;
- участник;
- время;
- тип контакта;
- краткое фактическое резюме;
- outcome code;
- связанные вопрос/возражение/обещание;
- нужен ли follow-up;
- ссылка на оригинал в исходной системе;
- уровень чувствительности.

### Журнал обучения

Структурированные записи:

- что открыто;
- что завершено;
- активное время;
- количество попыток;
- подтверждённый milestone;
- где ребёнок остановился;
- выбранная тема;
- следующий рекомендованный шаг;
- комментарий взрослого или преподавателя.

Не хранить поток движений, каждую паузу и полный ответ ребёнка, если они не нужны продукту.

### Дневник пробника

Одна запись на ключевой этап:

1. доступ создан;
2. письмо/бот доставил вход;
3. первый вход;
4. первый полезный результат;
5. повторный сеанс;
6. вопрос или барьер;
7. предложение;
8. оплата/отказ/окончание.

Для каждого этапа показывать факт, источник, время, ответственного и следующий шаг.

### Журнал продаж

- потребность, сформулированная клиентом;
- соответствующий продукт;
- обсуждённый оффер и его версия;
- возражение из справочника;
- ответ без скрытых обещаний;
- решение и причина;
- next contact date;
- причина потери;
- канал и сотрудник.

Оценки вроде «сложная мама» запрещены. Используется наблюдаемый факт: «просит письменное подтверждение условий до оплаты».

### Журнал поддержки

- категория и severity;
- проблема словами клиента;
- воспроизводимые факты;
- шаги диагностики;
- root cause;
- решение;
- SLA;
- удовлетворённость;
- повторное открытие.

### Журнал денег

Это интерфейс над ledger, а не ручной текст:

- заказ;
- попытки оплаты;
- успешный платёж;
- чек;
- период услуги;
- возврат/chargeback;
- кредит/бонус;
- сверка;
- связь с доступом.

### Журнал согласий

Append-only:

- purpose;
- статус;
- версия текста;
- источник;
- субъект и представитель;
- время;
- proof reference;
- отзыв и причина, если добровольно указана.

Согласие не редактируется задним числом.

### Журнал обещаний

- кто пообещал;
- кому;
- что именно;
- срок и timezone;
- ответственный;
- зависимость;
- статус;
- доказательство выполнения;
- причина просрочки.

Просроченное обещание выше по приоритету, чем маркетинговый контакт.

### Журнал решений

Нужен для нестандартных действий:

- вопрос;
- контекст;
- доступные варианты;
- решение;
- кто утвердил;
- дата;
- срок действия;
- последствия;
- ссылка на политику или договорённость.

### Журнал рисков и инцидентов

- риск/инцидент;
- затронутые семьи или системы;
- severity;
- containment;
- уведомления;
- восстановление;
- root cause;
- corrective action.

Чувствительные security-подробности хранятся не в общей карточке семьи.

### Дневник исследования и Voice of Customer

- добровольное интервью;
- контекст использования;
- цитата только при нужной цели;
- тема;
- потребность;
- барьер;
- продуктовый вывод;
- согласие на публикацию — отдельно;
- срок хранения сырой записи.

## 3. Универсальная запись дневника

| Поле | Описание |
|---|---|
| `journal_entry_id` | UUID |
| `family_id` | семья |
| `guardian_id`, `student_id` | необязательная привязка |
| `journal_type` | contact / learning / trial / sales / support / finance / consent / research / other |
| `entry_type` | тип по справочнику |
| `occurred_at` | когда произошло |
| `recorded_at` | когда записали |
| `author_type`, `author_id` | человек/система |
| `summary` | короткое фактическое резюме |
| `structured_data` | ограниченная JSON-схема типа |
| `source_reference` | ссылка на первоисточник |
| `sensitivity` | standard / restricted / highly_restricted |
| `visibility_scope` | owner / operations / support / finance / privacy |
| `correction_of` | исправляемая запись |
| `retention_class` | правило хранения |
| `created_from_event_id` | идемпотентность |

Запись не обновляется, если меняется исторический факт. Добавляется correction с причиной.

## 4. Шаблоны записей

### Резюме звонка

```text
Причина контакта:
Подтверждённые факты:
Вопрос клиента:
Что объяснили:
Решение клиента:
Обещание и срок:
Следующий шаг:
```

### Образовательное наблюдение

```text
Модуль/тема:
Что выполнено:
Что получилось:
Наблюдаемый барьер:
Рекомендованный следующий шаг:
Нужно ли участие взрослого/специалиста:
```

### Причина отказа

```text
Этап воронки:
Код причины:
Слова клиента без лишних данных:
Можно ли связаться позже:
Предпочтительный срок:
Что должно измениться для возврата:
```

## 5. Справочники вместо бесконечного текста

Структурировать:

- outcome;
- reason code;
- objection code;
- question topic;
- root cause;
- next action;
- severity;
- sentiment только как наблюдаемая реакция и с низкой уверенностью;
- продукт/курс/модуль;
- владелец проблемы.

Свободный текст остаётся для контекста, но не заменяет обязательные поля.

## 6. Правила хорошей заметки

Хорошая запись:

- краткая;
- фактическая;
- понятна другому сотруднику;
- не содержит унижений и ярлыков;
- отделяет слова клиента от вывода сотрудника;
- имеет следующий шаг;
- не дублирует секреты и платёжные реквизиты;
- не копирует всю переписку без необходимости;
- не обещает того, чего система не может выполнить.

Плохо: `Мама нервная, опять ничего не поняла.`  
Хорошо: `Родитель трижды уточнил дату списания; в письме не увидел период доступа. Нужно отправить письменное подтверждение тарифа и периода до 18:00.`

## 7. Автоматические резюме

ИИ может предложить черновик summary или classification только при следующих условиях:

- исходный контент обрабатывается в разрешённом контуре;
- PII и детские данные не уходят неизвестному провайдеру;
- сотрудник подтверждает запись до сохранения;
- сохраняется признак `ai_assisted`;
- выводы не становятся фактом автоматически;
- модель не ставит диагнозы, не решает вопрос возврата и не меняет согласия.

## 8. Семейная timeline

Единая шкала объединяет:

- заявки;
- контакты;
- пробники;
- обучение;
- задачи и обещания;
- платежи и возвраты;
- обращения;
- согласия;
- даты и milestones;
- UGC/реферальные события в разрешённом объёме.

Фильтры: `all`, `service`, `learning`, `money`, `communications`, `privacy`, `manual only`. По умолчанию скрываются highly restricted записи.

## 9. Daily log сотрудника

В конце дня автоматически формируется:

- новые семьи;
- незакрытые входящие;
- выполненные контакты;
- открытые обещания;
- просроченные задачи;
- критические платежи/возвраты;
- семьи без следующего шага;
- ручные изменения данных;
- ошибки интеграций.

Сотрудник добавляет только исключения и контекст. Повторный ручной ввод фактов запрещён.

## 10. Метрики качества памяти

- входящие без outcome;
- контакты без следующего шага при необходимости;
- обещания без срока;
- просроченные обещания;
- платежи, существующие только в заметках;
- записи без источника;
- доля свободного текста без классификации;
- исправления и спорные записи;
- просмотры restricted notes;
- среднее число повторных вопросов из-за отсутствия контекста.

## 11. Критерии приёмки

- timeline строится без дублирования одного события;
- оператор отличает «сообщение отправлено» от «обещание выполнено»;
- correction не стирает исходную запись;
- restricted заметки доступны только нужной роли;
- после входящего ответа автоматически создаётся задача, если обещан follow-up;
- финансовый факт берётся из ledger, учебный — из канонического источника;
- поиск работает по справочникам и разрешённому тексту;
- выгрузка клиента включает относящиеся к нему записи согласно политике;
- удаление/ограничение обработки применяется и к журналам;
- публичная база знаний содержит только шаблоны и синтетические примеры.
